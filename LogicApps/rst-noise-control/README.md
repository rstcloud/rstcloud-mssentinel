# Azure Logic App: Threat Intelligence Enrichment Playbook - RST Noise Control

## Summary

The provided Azure Logic App, titled "Enrich multiple entities - RST Noise Control," aims to automate threat intelligence enrichment for incidents generated by Microsoft Sentinel. This playbook integrates with the RST Cloud API to check if IP addresses, domains, URLs, and file hashes are well-known or benign values that usually produce False Positives.

## Prerequisites

- An Azure Key Vault.
- A Key Vault secret containing the RST Cloud API key.
- A system-assigned managed identity enabled on the Logic App.
- Least-privilege read access for that identity to the secret:
  - **Azure RBAC vaults:** `Key Vault Secrets User`, scoped to the Key Vault, or narrower where organisational policy supports it.
  - **Access-policy vaults:** secret `Get` permission — only if the vault uses access policies rather than Azure RBAC.
- The playbook's existing Microsoft Sentinel connection and permissions, which remain required for normal Sentinel operation.

The RST Cloud API key must **not** be configured as a Logic App workflow parameter.

## User Instructions

Follow these steps to set up and customise the playbook:

1. **Microsoft Sentinel Connection:**

   - Ensure the Microsoft Sentinel connection is configured in the `$connections` parameter and `connectionId`, `connectionName`, and `id` parameters are updated with the actual values.

2. **RST Cloud API Key (held in Azure Key Vault):**

   - Do not place the API key in a workflow parameter. Store it in Azure Key Vault and set the non-secret `keyvault_secret_uri` parameter to the versionless secret URI `https://<KEY_VAULT_NAME>.vault.azure.net/secrets/<SECRET_NAME>`.
   - See [RST API key storage](#rst-api-key-storage) for the full setup.

3. **Trusted Entities:**

   - Adjust the `trusted_domains`, `trusted_ips`, and `trusted_urls` parameters with your organisation's trusted entities.

4. **Review and Customise Actions:**

   - Review each "For Each" section (IP, URL, Hash) and adjust the actions based on your specific requirements.

5. **Deploy Logic App:**
   - Save and deploy the Logic App in your Azure environment.

## RST API key storage

The RST Cloud API key is never stored in this playbook. It is retrieved from Azure Key Vault at runtime by the `Get_RST_API_Key_from_Key_Vault` action, which authenticates using the Logic App's system-assigned managed identity against the Key Vault audience `https://vault.azure.net`. The retrieved value is used internally as the `X-Api-Key` header on the RST Noise Control HTTP requests.

That action has secure inputs and outputs enabled, so the secret is masked in Logic App run history. Do not view, copy, log, screenshot, or commit the secret value.

### Setup

1. Create or select a Key Vault.
2. Create a secret named `<SECRET_NAME>` holding the RST Cloud API key (`<RST_CLOUD_API_KEY>`) as its value.
3. Enable the system-assigned managed identity on `<LOGIC_APP_NAME>` in `<RESOURCE_GROUP>`.
4. Grant that identity `Key Vault Secrets User` on the Key Vault (Azure RBAC vaults), or secret `Get` (access-policy vaults).
5. Deploy or import the playbook.
6. Set the `keyvault_secret_uri` parameter to the versionless secret URI:

   ```text
   https://<KEY_VAULT_NAME>.vault.azure.net/secrets/<SECRET_NAME>
   ```

   Do not append a secret version unless a deployment deliberately pins one.

7. Confirm no API key value appears in any workflow parameter.

### Validation

1. Trigger the playbook from a controlled non-production Microsoft Sentinel incident or entity, following your organisation's test process.
2. Confirm `Get_RST_API_Key_from_Key_Vault` succeeds.
3. Confirm the relevant RST Noise Control lookup action runs.
4. Confirm the Key Vault action's inputs and outputs are masked in run history. Do not open or export them.
5. Keep API keys, request headers, tokens, callback URLs, and raw run-history data out of any test evidence.

### Key rotation

A versionless secret URI normally resolves to the current enabled version of the secret. To rotate the RST Cloud API key, add a new enabled version to the existing Key Vault secret and test the playbook with it before disabling the previous version. Disabling — not deleting — is the correct first rollback step. Avoid hard-coding a versioned URI unless pinning a version is a deliberate operational requirement.

## Playbook Functionality

- **Enrichment:** Utilises the RST Cloud API to fetch threat intelligence for IPs, domains, URLs, and file hashes associated with incidents.

- **Conditional Processing:** Includes logic to skip checking trusted and internal entities, optimising the enrichment process.

- **Comment Integration:** Adds enriched threat intelligence information as comments to the corresponding Microsoft Sentinel incidents.

- **Modular Design:** Separates processing for IP, URL, and hash entities, allowing for easy customisation and maintenance.

## Security Notes

- Apply least privilege: `Key Vault Secrets User` (or secret `Get`) and nothing broader.
- Never store the API key in Git, workflow parameters, workflow definitions, screenshots, logs, or tickets.
- Keep Key Vault network access aligned with your organisation's security policy while ensuring the Logic App can reach the vault.
- Keep secure inputs and outputs enabled on the secret-retrieval action.
- Review role assignments and rotate the RST Cloud API key regularly.
